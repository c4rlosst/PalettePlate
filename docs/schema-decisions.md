# Schema decisions

- USER becomes `users`, with a display name replacing separate first/second name fields. Profile region, gender, and contact number are optional; email is unique. DEVELOPER becomes a server-controlled `user`, `moderator`, or `admin` role. Auth accounts, sessions, verification records, and rate limits are separate MySQL tables managed through Better Auth's Drizzle adapter.
- `food_like_or_dislike` moves to `user_food_preferences`, unique per user/food. Absence means no preference. Preferences cascade on user/food deletion.
- FOOD stores Filipino/English names, colour, category, provenance, nullable per-100g nutrition fields, and a missing-data flag. Initial values are null. Foods are archived rather than removed when referenced by history or ingredients; restrictive foreign keys prevent accidental loss.
- ENTRY becomes `entries`, with an authenticated owner, meal type, and UTC timestamp. Date/time fields are combined; daily boundaries are Asia/Manila. `(user_id, eaten_at)` supports private day queries. The client never supplies the owning user ID.
- Entry foods and entry recipes become junctions. `entry_foods` snapshots colour/category when logged so later classification changes cannot rewrite past counts. Recipe logging is not exposed yet; implementation must expand ingredients into these snapshots within the entry transaction.
- RECIPE becomes `recipes` with an owner and `recipe_ingredients` child table (food plus human-readable amount). Ingredient colours are obtained from foods; recipe nutritional content is computed only when all required quantities and nutrient data are available, never fabricated. Recipe favourites become `favourite_recipes`.
- POST becomes `posts` with owner, optional recipe, content, timestamp, and draft/pending/approved/rejected moderation state. No public post endpoint exists in this slice; eventual public reads must require approved status. Initial MVP will use owner-only drafts and approved public posts rather than the ERD's unspecified privacy modes.
- Reactions and comments are child tables; one reaction per user/post. Shares and friends are deferred stretch goals and have no tables yet. When added they must use junctions, not arrays on USER/POST.
- Friend and entry counts are computed with scoped aggregate queries; no stored totals. They are not currently displayed.
- Attachments become `images`, storing private storage path, owner, MIME type, and positive size. Parent deletions are restricted while image rows exist; the eventual storage service must remove the object, then metadata, then parent. User deletion is also restricted by image ownership. This avoids silent orphaning from cascades. Uploads are not implemented yet.
- Owned profile/auth children, preferences, meals, draft recipes/posts, comments, and reactions cascade on owner deletion except restrictive history/image references. Recipe references in posts use SET NULL; logged recipes and foods use RESTRICT to protect history. Account deletion is not exposed; a later delete workflow must handle restrictive relationships explicitly.
- Foreign keys and primary/unique keys establish identity and referential integrity. Enums constrain roles, categories, colours, meal types, and statuses. Image size uses CHECK. Food-name indexes support sorted catalog queries; current contains-search is acceptable for the tiny starter catalog but cannot efficiently use a B-tree prefix. Revisit full-text search only when catalog size warrants it.
- User approved installed MySQL 9.6 for local work on November 10, 2026. Docker remains 8.4.7 for the originally specified target; migration compatibility must be checked on the eventual hosted patch before publishing.
